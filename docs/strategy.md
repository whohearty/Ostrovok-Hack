# Рабочая стратегия создания решения · draft
Статус: предложение ассистента на основе задания и поручений Максима 23.10.2026. Приложение пока не реализовано; исследования и метрики пока не проведены.

## Что оптимизируем
Пользователь получает выполнимый и понятный план поездки, может исправить ограничения и увидеть итоговое действие. Ключевая гипотеза: сочетание диалога, сравнения, таймлайна и проверок полной цены уменьшает усилие выбора относительно ручной сборки. Не обещаем доказанный рост конверсии. Поддерживаем разные составы группы и формулировки в явно объявленном покрытии каталога; семейный запрос — показательный случай, не жёсткое ограничение продукта.

## Сценарий и границы
1. Из первого сообщения собрать уже известные ограничения и отделить их от допущений.
2. Запросить только блокирующее: например, город отправления или общий бюджет. Не заставлять пользователя повторять сказанное.
3. Сопоставить 2–3 выполнимых варианта. По каждому показать состав цены, время, компромисс и происхождение данных.
4. Построить единый таймлайн и корзину. При изменении условий пересчитать связанные компоненты, сохранив остальные ограничения.
5. Получить явное подтверждение и создать mock-заказ. Показать, что это имитация.

Ни один из основных этапов пути не исключается ради красивого одного экрана. Минимизируем инфраструктуру: один веб-сервис, одна БД/локальный каталог, один адаптер модели и детерминированная проверка. Не нужны микросервисы, Kubernetes, RAG без корпуса, собственная платёжная система или автономная реальная покупка. Постпродажные действия, межсессионная память и мессенджер — backlog. Метрики качества включаем как наиболее полезную дополнительную функцию; полноценную мобильную разработку не планируем.

## Данные и технологии
Рабочее предложение — Python/FastAPI с простой HTML/JS-витриной, Pydantic-моделями и SQLite/JSON. Преимущество — одна сборка и быстрый запуск. Конкретные версии и провайдер LLM выбираются в технической пробе 26 октября, не по предположению об их текущей цене. Интерфейс провайдера сменный, без зависимости доменной логики от одной модели.

Для воспроизводимости основной каталог синтетический и версионированный:6–8 направлений,24+отеля, авиа/ЖД/трансферы, альтернативы с разными ограничениями. Это предлагаемый объём, не требование организаторов. Каталог генерируется для входных дат по объявленным правилам. Географическое покрытие показываем пользователю; запрос вне него не превращаем в выдуманный доступный отель. Опциональный открытый API подключаем только после готовности ядра и проверки прав/лимитов. Погода из синтетики или климатических данных не изображается актуальным прогнозом.
